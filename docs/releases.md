# GitHub publishing and releases

The CI workflow builds and publishes the server image to `ghcr.io/<owner>/<repository>`, using the lowercase GitHub repository path. It uses `GITHUB_TOKEN` with job-scoped `packages: write`; no personal access token or repository secret is needed for publishing. This follows [GitHub's package publishing workflow](https://docs.github.com/en/packages/managing-github-packages-using-github-actions-workflows/publishing-and-installing-a-package-with-github-actions).

## First push

The local repository already has its initial commit on `main`. Create an empty repository on GitHub, then add its remote and push. Replace `OWNER/REPOSITORY` with its repository path:

```sh
git remote add origin https://github.com/OWNER/REPOSITORY.git
git push -u origin main
```

The repository's default branch is detected automatically. CI runs Rust checks on Linux, macOS, and Windows, checks the Rust minimum version, runs the browser suite, and smoke-tests the Docker image. Publishing waits for all those jobs to pass. Pull requests and other branches run checks without publishing. A manual run from the default branch or a release tag can retry publishing.

The publishing job builds Linux AMD64 and ARM64 images, adds OCI source/revision labels, and publishes provenance and an SBOM. Its summary includes the image digest and tags. GitHub Actions dependencies for publishing are pinned to commits, with weekly Dependabot updates.

New GHCR packages are private by default. After the first successful publish, open your account or organization's **Packages → package → Package settings** and change visibility to public if users should pull without signing in. The workflow associates the package with its source repository. For an existing package, grant this repository Actions access in the package settings if needed. See [GitHub's container registry documentation](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry).

## Image tags

| Source                        | Published tags                                    |
| ----------------------------- | ------------------------------------------------- |
| Default branch                | `edge`, `sha-<full-commit-sha>`                   |
| Stable release, e.g. `v0.1.0` | `0.1.0`, `0.1`, `latest`, `sha-<full-commit-sha>` |

Release versions use numeric `MAJOR.MINOR.FIX`. `edge` tracks development; use an exact version or digest for a repeatable deployment. Tags and labels are generated by [Docker Metadata action](https://github.com/docker/metadata-action).

## Create a release

Follow the commit and release conventions in [AGENTS.md](../AGENTS.md). Use `MAJOR.MINOR.FIX`: increment MAJOR for breaking changes, MINOR for compatible features, or FIX for compatible bug fixes.

Set `workspace.package.version` in `Cargo.toml`, build the frontend with `npm --prefix web ci && npm --prefix web run build`, refresh `Cargo.lock` with `cargo check --workspace`, and commit both. The Git tag must be `v` followed by that exact version. The current version is `0.1.0`:

```sh
git tag -a v0.1.0 -m "0.1.0"
git push origin v0.1.0
```

The tag triggers the full CI pipeline and publishes the release image when checks pass. When creating the GitHub Release, use the bare version as its title, such as `0.1.1`. Its description contains bullet points summarizing changes since the previous released version, followed by the comparison link:

```markdown
- Fix interrupted download recovery.
- Improve account settings validation.

[Compare changes](https://github.com/OWNER/REPOSITORY/compare/v0.1.0...v0.1.1)
```

Replace the illustrative changes and tags with the actual release changes and versions. For the first release, list the initial functionality and replace the previous-version tag in the comparison link with the initial commit SHA (`git rev-list --max-parents=0 HEAD`). The tag push publishes the image independently of creating the GitHub Release.

## Run a published image

Copy `.env.example` to `.env` and set `BINBIN_IMAGE` to the real lowercase image path, such as `ghcr.io/owner/binbin:0.1.0`. Before the first versioned release, use `:edge`. Set `BINBIN_PUBLIC_URL` to the deployed origin.

```sh
cp .env.example .env
# Edit .env with the image path and public URL.
docker compose -f compose.release.yaml pull
docker compose -f compose.release.yaml run --rm binbin init-admin --username admin
docker compose -f compose.release.yaml up -d
```

Run `init-admin` only for a new data volume. For an existing deployment, keep its Compose project name when switching files so the same `binbin-data` volume is reused; use `-p EXISTING_PROJECT` if necessary. Both Compose files use the same volume key. `compose.release.yaml` pulls published images and requires no source build. `compose.yaml` remains the local source-build setup.

For a private package, first sign in to `ghcr.io` with `docker login ghcr.io --username YOUR_GITHUB_USERNAME`; paste a classic personal access token with `read:packages` into Docker's password prompt.

To update, set the desired image version or digest in `.env`, pull, then run `up -d`. Use the full digest reported by CI to pin an image:

```text
BINBIN_IMAGE=ghcr.io/owner/binbin@sha256:REPLACE_WITH_PUBLISHED_DIGEST
```

Keep the data-volume backup procedure in the README when changing application versions.
