# GitHub publishing and releases

The release workflow (`.github/workflows/release.yml`) runs only when a GitHub Release is published. It builds and publishes the server image to `ghcr.io/<owner>/<repository>` (lowercase repository path), attaches CLI binaries to the Release, and updates the Homebrew formula. Nothing runs on pushes or pull requests. Image publishing uses `GITHUB_TOKEN` with job-scoped `packages: write`; see [GitHub's package publishing workflow](https://docs.github.com/en/packages/managing-github-packages-using-github-actions-workflows/publishing-and-installing-a-package-with-github-actions).

## First push

Create an empty repository on GitHub, then add its remote and push. Replace `OWNER/REPOSITORY` with its repository path:

```sh
git remote add origin https://github.com/OWNER/REPOSITORY.git
git push -u origin main
```

## Release pipeline

1. `verify` checks that the release tag is `v` plus `workspace.package.version` in `Cargo.toml`, then runs `cargo test --locked --workspace --all-targets`.
2. `image` builds the image, smoke-tests it, then publishes Linux AMD64 and ARM64 images with OCI labels, provenance, and an SBOM. Its summary includes the digest and tags.
3. `cli` builds `binbin` for macOS (arm64, x86_64) and Linux (x86_64, arm64) and uploads `binbin-X.Y.Z-<target>.tar.gz` plus a `.sha256` file to the Release. Linux builds run on Ubuntu 22.04 runners to keep the glibc requirement low and need `libdbus-1` at runtime.
4. `homebrew` runs after `image` and `cli` succeed. It writes `Formula/binbin.rb` in `<owner>/homebrew-tap` and pushes it. Pre-releases skip this job.

Any failure stops later jobs. Re-running the workflow is safe: asset uploads overwrite, and the tap job skips the commit when the formula is unchanged.

### One-time setup

- Create the public repository `<owner>/homebrew-tap`, with at least one commit (a README is enough).
- Create a fine-grained personal access token limited to that repository with **Contents: read and write**, and store it as the Actions secret `HOMEBREW_TAP_TOKEN` in this repository.
- Install with `brew install <owner>/tap/binbin`.

New GHCR packages are private by default. After the first successful publish, open your account or organization's **Packages → package → Package settings** and change visibility to public if users should pull without signing in. The workflow associates the package with its source repository. For an existing package, grant this repository Actions access in the package settings if needed. See [GitHub's container registry documentation](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry).

## Image tags

| Source                        | Published tags                                    |
| ----------------------------- | ------------------------------------------------- |
| Stable release, e.g. `v0.1.0` | `0.1.0`, `0.1`, `latest`, `sha-<full-commit-sha>` |

Release versions use numeric `MAJOR.MINOR.FIX`. Use an exact version or digest for a repeatable deployment. Tags and labels are generated by [Docker Metadata action](https://github.com/docker/metadata-action).

## Create a release

Follow the commit and release conventions in [AGENTS.md](../AGENTS.md). Use `MAJOR.MINOR.FIX`: increment MAJOR for breaking changes, MINOR for compatible features, or FIX for compatible bug fixes.

Set `workspace.package.version` in `Cargo.toml`, build the frontend with `npm --prefix web ci && npm --prefix web run build`, refresh `Cargo.lock` with `cargo check --workspace`, commit both, and push to the default branch. The current version is `0.3.0`. Then publish the Release, which creates the tag and starts the pipeline. The title is the bare version and the description is bullet points followed by the comparison link:

```sh
gh release create v0.1.1 --target main --title 0.1.1 --notes-file notes.md
```

```markdown
- Fix interrupted download recovery.
- Improve account settings validation.

[Compare changes](https://github.com/OWNER/REPOSITORY/compare/v0.1.0...v0.1.1)
```

Replace the illustrative changes and tags with the actual release changes and versions. For the first release, list the initial functionality and replace the previous-version tag in the comparison link with the initial commit SHA (`git rev-list --max-parents=0 HEAD`).

## Run a published image

Copy `.env.example` to `.env` and set `BINBIN_IMAGE` to the real lowercase image path, such as `ghcr.io/owner/binbin:0.1.0`. Set `BINBIN_PUBLIC_URL` to the deployed origin.

```sh
cp .env.example .env
# Edit .env with the image path and public URL.
docker compose -f compose.release.yaml pull
docker compose -f compose.release.yaml run --rm binbin init-admin --username admin
docker compose -f compose.release.yaml up -d
```

Run `init-admin` only for a new data volume. For an existing deployment, keep its Compose project name when switching files so the same `binbin-data` volume is reused; use `-p EXISTING_PROJECT` if necessary. Both Compose files use the same volume key. `compose.release.yaml` pulls published images and requires no source build. `compose.yaml` remains the local source-build setup.

For a private package, first sign in to `ghcr.io` with `docker login ghcr.io --username YOUR_GITHUB_USERNAME`; paste a classic personal access token with `read:packages` into Docker's password prompt.

To update, set the desired image version or digest in `.env`, pull, then run `up -d`. Use the full digest reported by CI to pin an image:

```text
BINBIN_IMAGE=ghcr.io/owner/binbin@sha256:REPLACE_WITH_PUBLISHED_DIGEST
```

Keep the data-volume backup procedure in the README when changing application versions.
